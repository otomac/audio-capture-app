# 00 — 進め方の法（Ways of Working）

すべての作業に無条件で適用される。個別タスクの指示より優先度が高い。
「今回だけ」は無い。守れない事情があるなら、[README.md §5](./README.md#5-規範を変えたいとき) の手順で規範のほうを直す。

---

## 法 1 — タスク先行

**タスクを起票していない作業は、行ってはならない。**

- 実装・修正・リファクタリング・ハーネス変更のいずれも、まず `docs/tasks/backlog.md` に起票する。
- 起票せずに始まった作業は、気づいた時点で中断して起票する。
- **進捗はタスク台帳でのみ管理する。** 会話の中の「終わりました」は進捗ではない。台帳の状態を更新して初めて進捗になる。
- タスクの粒度・状態遷移・様式は [60-task-format.md](./60-task-format.md) に従う。

**なぜ。** 作業の単位が明示されていないと、どこまでが今回のスコープかが誰にも分からなくなり、
「ついでの修正」が混入し、レビューが不能になる。タスク票はスコープの契約書である。

**強制。** `.cs` / `.xaml` を編集しようとしたとき、台帳に進行中（`[~]`）のタスクが 1 件も無ければ
`guard-source-edit.ps1` が確認を求める。

### やってはいけないこと

- 依頼された作業の「ついで」に、無関係なファイルを直す。
- 1 つのタスク票に、独立した複数の目的を詰め込む。
- 完了していないタスクを `[x]` にする。

## 法 2 — 仕様書先行

**仕様が変わるなら、ソースコードより先に `docs/spec/` を直す。**

- `docs/spec/` が **唯一の正** である。他の場所（README・コメント・過去の会話）と食い違ったら `docs/spec/` が勝つ。
  - ただし **仕様書とコードが食い違ったときはコードが事実**（現に動いているものが真実）。その場合は
    「仕様書が古い」というバグとしてタスクを起票し、仕様書を現実に合わせる。
- 順序は **仕様書 → 実装** であって、逆ではない。実装してから仕様書を後追いで書くのは禁止。
- 仕様に影響しない変更（内部リファクタリング、テスト追加、ビルド設定）は仕様書更新の対象外。
  ただし [20-architecture-standards.md](./20-architecture-standards.md) に触れる変更は
  `docs/spec/02_architecture.md` と `03_class_diagram.md` の更新対象になりうる。
- どの章を更新すべきかは [50-spec-standards.md](./50-spec-standards.md) の対応表に従う。

**なぜ。** 仕様書を後追いにすると必ず書かれないまま終わる。先に書くと、実装前に矛盾と抜けが見つかる
（設計レビューの最も安いタイミング）。

**強制。** `AudioCaptureApp/` 配下の `.cs` / `.xaml` を編集しようとしたとき、`docs/spec/` に未コミットの
変更が 1 つも無ければ `guard-source-edit.ps1` が確認を求める。仕様に影響しない変更なら承認して進めてよい。

---

## 法 3 — アーキテクチャ優先

**3 層構成（Models / ViewModels / Services）と依存方向は、実装の都合で曲げない。**

- 規範の本体は [20-architecture-standards.md](./20-architecture-standards.md)。
- 「速いから」「そのほうが短いから」は層を跨ぐ理由にならない。
- **アーキテクチャを変える必要が本当にあるなら、実装する前に ADR を書く**
  （`docs/adr/`、様式は [templates/adr.md](./templates/adr.md)）。ADR なしの構造変更は差し戻し対象。
- ADR が必要になる変更の例：
  - 層の追加・削除、依存方向の変更
  - DI コンテナの導入（現在は意図的に不使用）
  - `MainViewModel` の分割（現在は意図的に 1 ファイル集約）
  - Service 層への抽象化レイヤー（インターフェース）の導入
  - 新しい外部ライブラリの採用

**なぜ。** 構造の破れは局所的なコード品質と違い、後から直す費用が跳ね上がる。
そして構造は「なぜそうしたか」を残さないと、次の担当者が善意で壊す。

### ライブラリ追加は個別承認制

**新しい NuGet パッケージを、承認なしに導入・前提・既定にしてはならない。**
BCL または最小限の自前実装を優先する。ライブラリが必要に見えたら、止めて
「ライブラリ案」と「ライブラリなし案」の両方を提示する。1 つの承認は別のパッケージの承認を意味しない。

## 法 4 — 品質ゲート

**静的解析とユニットテストの両方をクリアするまで、「完了」と言ってはならない。**

ゲートは 3 つ。定義と実行方法は [40-quality-gates.md](./40-quality-gates.md)。

| # | ゲート | コマンド | 合格条件 |
|---|---|---|---|
| G1 | ビルド＋静的解析 | `dotnet build AudioCaptureApp.slnx -c Debug` | 警告 0 件（警告はエラー扱い） |
| G2 | 書式・スタイル | `dotnet format AudioCaptureApp.slnx --verify-no-changes` | 差分 0 |
| G3 | ユニットテスト | `dotnet test AudioCaptureApp.slnx -c Debug` | 全件成功、失敗 0 |

- **アナライザー・テストを無効化して通してはならない。** 原因を直す。
  やむを得ない抑止は、対象を最小範囲に絞り、理由を 1 行で添える（[40-quality-gates.md](./40-quality-gates.md) の書式）。
- **実行結果を示さずに「通りました」と言ってはならない。** 実際の件数を書く
  （「テストが通る」ではなく「42 件成功 / 0 件失敗」）。

## 横断ルール

### 事実に基づく

- 主張には根拠を付ける。コマンド出力・`ファイル:行` の引用を示す。
- 情報源の優先順位（上が強い）：**① コード → ② 実行時の観測結果 → ③ 文書（仕様書・ハーネス・CLAUDE.md） → ④ 過去の AI 出力**。
  文書は「確認すべき手がかり」であって権威ではない。食い違ったらコードが勝ち、ズレを記録する。
- 検証していないことは「未検証」と明示する。「たぶん動く」は書かない。

### ブランチ運用

**新しいタスクに着手するときは、最新の `develop` から作業ブランチを切る。**
`develop` / `main` の上で直接ソースを編集してはならない。

1. **最新化** — `git switch develop` → `git pull --ff-only origin develop`
2. **ブランチ作成** — `git switch -c <接頭辞>-<slug>`（下の接頭辞表に従う）
3. **統合** — 品質ゲート G1/G2/G3 が **すべて緑になってから** `commit` → `push` → PR 作成（宛先は `develop`）

| 接頭辞 | 使う場面 | 例 |
|---|---|---|
| `feature-` | 新機能・機能変更 | `feature-speaker-diarization` |
| `fix-` | バグ修正 | `fix-gpu-toggle-and-model-load` |
| `maintenance-` | ビルド設定・依存更新・ハーネス変更 | `maintenance-fix-warnings` |

- **1 タスク = 1 ブランチ。** 複数タスクの変更を 1 ブランチに混ぜない。
- 台帳（`docs/tasks/backlog.md`）への起票も、そのタスクのブランチ上で行う。PR の差分に含める。
- **ゲートが緑になる前に commit しない。** 「途中まで push」もしない。
- `main` へは `develop` からのみ入る。作業ブランチから `main` へ PR を出さない。

**なぜ。** `develop` 以外を起点にすると、まだ統合されていない別タスクの変更を巻き込み、PR の差分が
「そのタスクの変更」ではなくなってレビューできない。ゲート未通過のコミットを積むと、
どの時点が緑だったのかが履歴から失われる。

**強制。** `develop` / `main` / `master` 上で `.cs` / `.xaml` を編集しようとすると
`guard-source-edit.ps1` が **deny** で止める。`git switch` / `commit` / `push` / `gh pr create` は
`protect-commands.ps1` が都度確認する。

### 不可逆な操作は都度確認

- `git commit` / `push` / `amend` / ブランチ切替 / PR 作成は、**その都度** 明示的な依頼があるときだけ行う。
  1 つの承認（commit）は別の操作（push）の承認ではない。
- force push、共有履歴の書き換え、`git reset --hard`、ファイル削除は事前確認必須。
- 自分が作っていないファイルを削除・上書きするときは、先に中身を確認して申告する。

**強制。** `protect-commands.ps1` が破壊的コマンドを `deny` / `ask` で止める。

### スコープを守る

- 依頼されたことだけを行う。頼まれていないリファクタリングはしない。
- 起こりえないケースへの防御コードや、使う予定のない抽象化を足さない。
- 既存のパターンに合わせる。周囲のコードと違う書き方を持ち込まない。
