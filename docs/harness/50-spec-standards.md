# 50 — 仕様書の規範

**法 2（仕様書先行）の本体。**

## 1. 正はひとつ

**`docs/spec/` が仕様の唯一の正である。**

| 場所 | 位置づけ |
|---|---|
| `docs/spec/` | **正。** 現行仕様。常に最新の実装と一致していること |
| `docs/archive/initial-spec-kit/` | 初期構築時（2026-03）の spec-kit 形式の記録。**参照専用・更新しない** |
| `README.md` / `manual/` | 利用者向けの説明。仕様の正ではない |
| コード内コメント | 実装の意図。仕様の正ではない |
| **上記以外の場所** | **禁止。** 仕様文書を置いてはならない（下の §1.1） |

食い違ったときの優先順位は [00-ways-of-working.md](./00-ways-of-working.md#事実に基づく) の通り：
**コード > 実行時の観測 > 仕様書**。仕様書とコードがずれていたら、それは「仕様書のバグ」であり、
起票して仕様書を現実に合わせる。

### 1.1 `docs/spec/` の外に仕様文書を作らない

**新しいディレクトリを掘って設計文書・仕様文書を置くことを禁止する。**
ツールや支援エージェント（superpowers 等）が `docs/superpowers/specs/` のような
独自の置き場を提案・生成してきた場合も同じで、**採用しない**。書きたい内容の行き先は
必ず次の 3 つのいずれかである。

| 書きたいもの | 正しい行き先 |
|---|---|
| アプリの振る舞い・構成・処理順序（＝仕様） | `docs/spec/` の該当する章（§2 の対応表） |
| 構造に関わる決定と、その理由・却下案（＝アーキテクチャ決定） | `docs/adr/NNNN-<slug>.md`（[templates/adr.md](./templates/adr.md)） |
| 1 タスク分の実装計画・スコープ境界・テスト一覧 | `docs/tasks/<ID>-<slug>.md`（[templates/task.md](./templates/task.md)） |

置き場の一覧は [CLAUDE.md の「ドキュメントの置き場」](../../CLAUDE.md) が持つ。**この表に無い場所は作らない。**

**なぜ。** 仕様文書が 2 か所にあると、片方だけが更新されて必ず食い違う。
実例：`docs/superpowers/specs/2026-08-19-silence-cut-before-whisper-design.md`（T112 の設計文書）は
`docs/tasks/T112-silence-cut-before-whisper.md` と内容が重複したまま放置され、その後 T125 が
足切り条件を、T129 が確定契機を改訂したのに追随せず、**現行仕様と食い違う古い記述**になっていた（T133 で削除）。
`docs/spec/` は法 2 と `guard-source-edit.ps1` で更新が強制されるが、
表に無い場所には強制が一切かからないため、腐るのは時間の問題である。

## 2. 章立てと更新対象の判定

| ファイル | 内容 | この変更をしたら更新する |
|---|---|---|
| [00_overview.md](../spec/00_overview.md) | アプリ概要・文書構成・対象範囲外 | 対象範囲そのものが変わったとき、章を増減したとき |
| [01_requirements.md](../spec/01_requirements.md) | 機能要件・非機能要件（`REQ-XXX-NN` 付き） | **機能の追加・変更・削除**。ユーザーから見た振る舞いが変わるすべて |
| [02_architecture.md](../spec/02_architecture.md) | 技術スタック・レイヤー構成・スレッドモデル・データフロー・永続化・エラー方針 | 層構成、依存関係、スレッド、保存先、ライブラリ、エラー方針の変更 |
| [03_class_diagram.md](../spec/03_class_diagram.md) | Mermaid クラス図 | 公開クラス／主要メソッド・プロパティの増減、クラス間関係の変更 |
| [04_sequence_diagram.md](../spec/04_sequence_diagram.md) | Mermaid シーケンス図 | 処理順序・呼び出し関係の変更、ユースケースの追加 |

### 更新が不要な変更

- 内部リファクタリング（外から見た振る舞いも公開シグネチャも変わらない）
- テストの追加・修正
- ビルド設定・CI・ハーネス自体の変更
- 静的解析警告の解消（振る舞いを変えない範囲で）

判断に迷ったら **更新する側に倒す**。

## 3. 書き方の規約

### 要件 ID

`01_requirements.md` の要件は `REQ-<領域>-<連番 2 桁>` で採番する（`REQ-DEV-01`、`REQ-REC-04` 等）。

- **ID は再利用しない。** 削除した要件の番号を別の要件に振り直さない。
- 各要件に **実装箇所**（クラス名・メソッド名）を付記する。既存の表形式を踏襲する。
- 要件を削除するときは行ごと消す（打ち消し線を残さない）。履歴は git が持っている。

### Mermaid 図

- クラス図・シーケンス図はコードから読み取れる **事実** を書く。願望や将来計画を混ぜない。
- 要件理解に必要なメンバーに絞る。全メンバーを列挙しない。
- `[ObservableProperty]` / `[RelayCommand]` によるソースジェネレータ生成分は、
  **生成前のフィールド／メソッド定義** をもとに表現する（既存の方針を踏襲）。

### 相互リンク

章をまたぐ参照は相対リンクで張る。リンク切れはレビューで指摘する。

## 4. 手順

[10-workflow.md](./10-workflow.md) の S3。要点だけ再掲する。

1. §2 の対応表で **更新対象の章を特定** する。
2. **実装より先に** 仕様書を直す。
3. 実装が終わったら仕様書を **読み直す**。実装が計画からずれていたら、仕様書を実装に合わせる。

**強制。** `AudioCaptureApp/` 配下の `.cs` / `.xaml` を編集しようとしたとき、`docs/spec/` に
未コミットの変更が無ければ `guard-source-edit.ps1` が確認を求める。
仕様に影響しない変更（§2「更新が不要な変更」）なら承認して進めてよい。

## 5. 大きな仕様変更のとき

複数の章に跨る変更や、既存要件と矛盾しうる変更では、まず
[templates/spec-change.md](./templates/spec-change.md) で **変更提案** を書いて承認を得てから
`docs/spec/` に反映する。提案そのものはタスク詳細ファイル（`docs/tasks/<ID>-<slug>.md`）に含めてよい。
