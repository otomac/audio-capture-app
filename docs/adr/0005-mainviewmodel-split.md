# ADR-0005 — `MainViewModel` を分割するか（ADR-0002 の再評価）

> **状態:** 承認済み
> **日付:** 2026-08-27（起草 2026-08-26）
> **関連タスク:** [T155](../tasks/T155-viewmodel-split-adr.md)（本 ADR）/ [T154](../tasks/T154-ui-refresh.md)（本 ADR の結論を待って再開）
> **関連 ADR:** [ADR-0001](./0001-baseline-architecture.md)（3 層 / DI なし / 抽象なし）、
> [ADR-0002](./0002-secondary-windows-share-mainviewmodel.md)（補助ウィンドウは `MainViewModel` を共有する）

## 背景

[T154](../tasks/T154-ui-refresh.md)（UI の改良）で **4 枚目のウィンドウ `SettingsWindow`** を足すことになった。

ADR-0002 は「結果」の節で、**自ら再評価の契機を指定している。**

> **悪くなること・受け入れるコスト:** `MainViewModel` が太る。実測で 767 行 → **788 行**
> （T113 / T114 の追加後）。分割の閾値 1,500 行にはまだ距離があるが、
> **ウィンドウが 4 枚目・5 枚目と増えるなら、この ADR を置換して案 A を選び直すことになる。**

つまり「4 枚目を足すときに考え直す」と当時の自分が書き残している。T154 がその 4 枚目にあたる。
**この条項に触れた以上、黙って 4 枚目を足すことはできない**（法 3 — アーキテクチャ優先）。

あわせて `MainViewModel.cs` は ADR-0002 の記述時から **788 行 → 1,396 行**へ育っている。
[20-architecture-standards.md §6](../harness/20-architecture-standards.md#6-構造が壊れかけているサイン)
の分割の閾値 1,500 行に対して **93%** の位置にいる。

## 現状

### 実測（2026-08-26 時点）

| 項目 | ADR-0002 記述時（2026-08-20） | 現在 |
|---|---|---|
| `MainViewModel.cs` の行数 | 788 | **1,396** |
| うちコード行（空行・コメントを除く） | — | 922 |
| うち XML ドキュメントコメント | — | 214 |
| うち行コメント | — | 75 |
| 空行 | — | 185 |
| 分割の閾値 | 1,500 | 1,500 |
| ウィンドウ枚数 | 3 | 3（T154 で **4**） |
| `[ObservableProperty]` の数 | — | 28 |
| `[RelayCommand]` の数 | — | 10 |

T154 が増やすのは概算 **+10 行**（`SettingsRequested` / `ShowSettings` / `CanShowSettings` の追加と、
`IsSpeakerDiarizationReady` / `IsSpeakerDiarizationReadyFor` の削除の差引）で、約 1,406 行になる。
**閾値は超えないが、残りは約 100 行である。**

### ADR-0002 の前提は、どこが今も正しく、どこが崩れたか

ADR-0002 が案 A（ウィンドウごとの ViewModel）を却下した決め手はこうだった。

> **欠点:** 3 つのウィンドウが**同じ状態**（`IsTranscribingFile`・進捗・文字起こし結果）を
> 見るため、ViewModel 間で状態を同期する仕組みが要る。

**この前提の前半は、現在のコードでは成り立っていない。** 各ウィンドウの XAML が実際に
バインドしているプロパティを数えると、3 つの集合は**完全に素**である。

| ウィンドウ | バインドしているプロパティ数 | 他ウィンドウとの重複 |
|---|---|---|
| `MainWindow` | 33 | **0** |
| `FileTranscriptionOptionsWindow` | 11 | **0** |
| `LiveTranscriptWindow` | 1（`LiveTranscriptLines`） | **0** |

**一方、後半（同期の仕組みが要る）は今も正しい。** 見る側は分かれているが、**書く側が跨っている**。

| 共有されている状態 | 誰が書くか | 誰が見るか |
|---|---|---|
| `IsNotBusy` = `!IsRecording && !IsStopping && !IsTranscribingFile`（`MainViewModel.cs:562`） | 録音とファイル文字起こしの両方 | `MainWindow` のほぼ全操作の可否 |
| `StatusMessage` | 録音・デバイス・モデル読み込み・**ファイル文字起こしの完了/失敗/中止**（1235 / 1256 / 1262 / 1268 / 1276 行） | `MainWindow` のステータスバー |
| `LastResultPath` | 録音停止（959 行）と**ファイル文字起こし完了**（1257 行） | `MainWindow` の「保存先を開く」 |
| `LiveTranscriptLines` | `TranscriptionService.SegmentTranscribed`（**ライブとファイルの両方**が発火する） | `LiveTranscriptWindow` |

したがって正確には、**「画面は分かれているが、状態の書き手が画面をまたいでいる」**。
分割するなら必要になるのは「同じ値を 2 か所に持って同期する仕組み」ではなく、
**子から親へ結果を返す経路**である。これは案 A の欠点として ADR-0002 が想定したものより軽い。

### 責務の集中

`MainViewModel` は現在おおよそ次の 10 個を持っている。
デバイス管理 / 録音制御 / ミュート / レベルメーター / 設定の永続化 / Whisper モデルの読み込み /
ライブ文字起こし / ファイル文字起こしの進行管理 / 話者識別の状態 / 成果物フォルダ。

ファイル文字起こしとライブ表示に関わる記述は **198〜583 行と 1,142〜1,293 行に集中**しており、
概算で **500〜600 行**である（他の関心と行が交錯しているため厳密な値ではない）。

## 選択肢

### 案 A — ウィンドウごとに ViewModel を作る（ADR-0002 が想定した「選び直し」先）

- **内容:** `FileTranscriptionViewModel` / `LiveTranscriptViewModel` / `SettingsViewModel` を新設し、
  各ウィンドウの `DataContext` にする。`MainViewModel` は共有状態（`IsNotBusy` の元・`StatusMessage`・
  `LastResultPath`）を持ち、子 ViewModel はコンストラクターで親への参照を受け取る（DI もメッセンジャーも使わない）。
- **利点:** 各ウィンドウの関心が独立し、`MainViewModel` が概算 800〜900 行まで下がる。
  ウィンドウを 5 枚目・6 枚目と足しても親が太らない。ViewModel 単位のテストが書きやすくなる。
- **欠点:** **子 → 親の参照が双方向の依存になる**（親が子を生成し、子が親を呼ぶ）。
  `IsNotBusy` のように「子の状態から親の可否が決まる」値は、子が変わったことを親へ伝え、
  親が `OnPropertyChanged` を出し直す配線が要る。**この配線は現在は不要である**（同一オブジェクトなので勝手に一致する）。
  `CLAUDE.md`「ViewModel は `MainViewModel.cs` 1 ファイルに集約」の変更も要る。
- **影響範囲:** `ViewModels/` に 3 ファイル追加、`MainViewModel` から約 500〜600 行の切り出し、
  4 つの `.xaml.cs` の `DataContext` 差し替え、既存テストの参照先変更、`CLAUDE.md`、
  `20-architecture-standards.md` §5、`docs/spec/02_architecture.md` / `03_class_diagram.md`。
  **T154 とは別タスクになる規模。**

### 案 B — 現状維持（ADR-0002 のまま 4 枚目を足す）

- **内容:** `SettingsWindow` も `MainViewModel` を共有する状態レス View として足す。ADR-0002 は無変更。
- **利点:** 実装量ゼロ。状態同期の配線が一切要らない。T154 が即座に進む。
- **欠点:** **ADR-0002 が自ら書いた再評価の条項を、根拠を示さずに素通りすることになる。**
  次に誰かが 5 枚目を足すとき、同じ問いがもう一度、しかも今より悪い条件（閾値により近い）で発生する。
  閾値 1,500 行までの余裕が約 100 行しかなく、**次の中規模タスクで超える**可能性が高い。
- **影響範囲:** なし。

### 案 C — 部分分割（ファイル文字起こしとライブ表示だけを切り出す）

- **内容:** 案 A のうち `FileTranscriptionViewModel` と `LiveTranscriptViewModel` だけを作る。
  `SettingsWindow` は `MainViewModel` を共有したままにする（設定 5 項目はいずれも
  `MainWindow` が持っていた状態であり、切り出しても親と密に結びつくため）。
- **利点:** 効果の大きいところ（500〜600 行）だけを取り、配線の要る箇所を最小にする。
- **欠点:** **「ウィンドウごとに ViewModel」という規則にならない。**「どのウィンドウが自前の
  ViewModel を持つか」が場当たりになり、次の担当者が判断できない。規則として弱い。
- **影響範囲:** 案 A から `SettingsViewModel` を除いたもの。

### 案 D — ViewModel は 1 個のまま、`partial` でファイルを分割する

- **内容:** クラスは `MainViewModel` 1 個のまま、`MainViewModel.FileTranscription.cs` /
  `MainViewModel.LiveTranscript.cs` / `MainViewModel.Recording.cs` のように **`partial class` で
  ファイルだけを機能単位に割る**。`DataContext` は全ウィンドウで従来どおり `MainViewModel`。
- **利点:** **状態同期の配線がゼロのまま、1 ファイルあたりの行数だけが下がる**（1,396 行 → 300〜500 行 × 3〜4）。
  ADR-0001（DI なし・抽象なし）にも ADR-0002（補助ウィンドウは共有）にも一切触れない。
  実測されている唯一の問題（1 ファイルが読みづらい）に直接効く。後から案 A へ移るときも、
  切り出す境界が既にファイルとして引かれているぶん**むしろ楽になる**。
- **欠点:** **責務の集中そのものは解消しない。** クラスは 1 つのままなので、
  「どのプロパティがどのウィンドウのものか」はファイル名でしか分からず、コンパイラは何も強制しない。
  `CLAUDE.md`「`MainViewModel.cs` 1 ファイルに集約」の文言変更が要る（1 ファイル → 1 クラス）。
  20-architecture-standards.md §6 の閾値も「クラスの行数」として読み替える必要がある。
- **影響範囲:** `ViewModels/` のファイル分割のみ。`CLAUDE.md`、`20-architecture-standards.md` §6、
  `docs/spec/02_architecture.md` の 1 行。**public な形は 1 バイトも変わらないため、テストは無変更。**

## 決定

**案 D を採り、案 A は「1,500 行を超えたとき」または「5 枚目のウィンドウを足すとき」に再評価する。**

決め手になった観点：

- **実装量とリスク** — 実測されている問題は「1 ファイル 1,396 行が読みづらい」だけである。
  案 D はそれに直接効き、`public` な形も実行時の挙動も変えない。テストも無変更で、
  品質ゲートで壊れていないことをそのまま確認できる。案 A は 500〜600 行を動かし、
  4 つの `.xaml.cs` と既存テストを触る。**T154 を止めている間に払うコストとして重い。**
- **依存の増減** — 案 A は親子の**双方向参照**を持ち込む。現在は `IsNotBusy` が
  同一オブジェクト上の 3 つのフラグから導かれているだけで、配線は 1 本も無い。
  分割するとこれが「子の変更を親へ伝える」明示的な配線になり、**伝え忘れが新種のバグになる**
  （録音中なのにデバイスが選べてしまう、等）。今それを買う理由が無い。
- **ADR-0002 の条項の趣旨** — あの条項が守ろうとしていたのは「`MainViewModel` が太ること」である。
  太りに対処するのが目的なら、案 D はそれを満たす。**ウィンドウの枚数そのものは問題ではなかった**
  ことが、バインド集合が完全に素であるという実測から分かる。
- **後戻りのしやすさ** — 案 D を選んでも案 A への道は塞がらない。むしろ機能ごとにファイルが
  割れているぶん、切り出しは容易になる。逆に案 A を今選ぶと、後から「やっぱり 1 個でよかった」へ
  戻すほうが高くつく。

**案 B を採らない理由:** 条項を素通りすると、同じ問いが 5 枚目でもう一度、
しかも閾値をまたいだ状態で発生する。**今回の再評価そのものは行うべきである。**
ただし再評価の答えが「案 A へ全面移行」である必要はない。

**案 C を採らない理由:** 「どのウィンドウが自前の ViewModel を持つか」の規則を作れないため。
規則にできない構造は、次の担当者が判断できない。

### この決定に伴う規則（案 D を採る場合）

1. **`MainViewModel` は 1 クラスのまま。** `DataContext` は全ウィンドウで同じインスタンスを共有する
   （ADR-0002 の規則 1〜5 はすべてそのまま有効）。
2. **ファイルは機能単位で `partial` に割る。** 1 ファイル 500 行を目安とする。
3. **`ViewModels/` に `MainViewModel` 以外のクラスを置かない。** 置きたくなったら本 ADR を置換する。
4. **再評価の契機を 2 つ置く** — ①`MainViewModel` の**全ファイル合計**が 1,500 行を超えたとき、
   ②**5 枚目のウィンドウ**を足すとき。どちらかに触れたら案 A を改めて検討する。
   （ADR-0002 の「4 枚目」条項は本 ADR の①②で置き換える。）

## 結果

- **良くなること:** 1 ファイルあたりの行数が 1,396 → 300〜500 に下がり、読む範囲が絞れる。
  T154 が最小の遅れで再開できる。再評価の契機が「行数」と「枚数」の 2 つに明文化され、
  次に同じ問いが出たときの判断材料が残る。
- **悪くなること・受け入れるコスト:** 責務の集中は残る。`MainViewModel` は引き続き 10 個の関心を持ち、
  ViewModel 単位のテストは書けないままである（現在も書けていない）。
  `CLAUDE.md` と `20-architecture-standards.md` の文言修正が要る。
  **そして、いずれ案 A をやることになる可能性は高い** — 先送りであることを認める。
- **後戻りのしやすさ:** 非常に高い。`partial` を 1 ファイルへ戻すだけで元に戻る。
  案 A へ進む場合も、切り出す境界が既に引かれている。
