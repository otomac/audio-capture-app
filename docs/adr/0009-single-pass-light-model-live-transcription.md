# ADR-0009 — ライブ文字起こしを「軽量モデル × 短い区切り」の 1 段にする（速報パスは既定 OFF）

> **状態:** 承認済み（2026-11-23、利用者）— 案 A。[T199](../tasks/T199-light-model-single-pass.md) の実測で決めた。
> **日付:** 2026-11-23
> **関連タスク:** [T199](../tasks/T199-light-model-single-pass.md)（実測と判断）/ T200・T201（実装。T199 の C3 で起票）
> **関連 ADR:** [ADR-0007](./0007-two-pass-live-transcription.md)（速報パスと確定パスの 2 段。本 ADR が置き換える）

## 背景

利用者の依頼（2026-11-04）:

> 速報を作るよりも、軽いモデルでの出力間隔を短くする方向のほうがいいかもしれない。
> base にすると、文字起こし自体の精度は当然下がるが、議事録化する上ではそこまで支障がないと思われる。small-q5_1 でも良さそう。

ADR-0007 の 2 段構成には、使ってみて次の不都合がある。

- **確定の文が遅い。** 速報は 1〜2 秒で出るが、ファイルに残る確定の文は、今の構成（small × 上限 10 秒 × 発話終了の無音 2.0 秒）だと
  発話から p50 8.3 秒 / p95 13.4 秒遅れる（T199 の M4。Zoom なし）。Zoom 中は p50 8.8 秒 / p95 16.4 秒。
- **Zoom 中に確定パスが追いつかない。** 2 音源に同じ音声を流す条件で、滞留が 60 秒を超える（T182 で最大 143 秒、T199 の M5 で 92.6 秒）。
  速報の有無とは関係なく起きている（ADR-0007「決定」）。
- **速報は CPU を Zoom と取り合う**（T182 で CPU の p95 22〜23%）。速報用モデルが 1 つ多く常駐し、スレッドも 1 本多い。
- 議事録に使うのは確定の文なので、速報の速さは議事録の役に立たない。

## 現状

- ライブ文字起こしは 2 段（ADR-0007 案 B）。確定パスは専用スレッド `WhisperTranscription` が GPU で回し、
  速報パスは `ProvisionalTranscription`（CPU・4 スレッド・`BelowNormal`）が並列に回す
  （[02_architecture.md §4](../spec/02_architecture.md#4-スレッドモデル)）。速報の既定は ON（REQ-CFG-12）。
- 確定パスの区切りは、遅れていないとき上限 10 秒・遅れているとき 20 秒（REQ-TRX-LIVE-10）。
  発話終了の無音は `MergeGapSeconds` 2.0 秒（REQ-TRX-LIVE-13）で、ファイル文字起こしの無音分割
  `SilenceMergeGapSeconds`（REQ-CFG-06）と同じ値を共用している。区切りの上限は定数で、設定にない。
- ライブ用のモデルは登録済みモデル（REQ-CFG-08）から利用者が選ぶ。

## 選択肢

T199 で、モデル {small, small-q5_1, base} × 上限 {4, 6, 10 秒} × 発話終了の無音 {0.8, 2.0 秒} の 18 構成を測り（M2）、
絞り込んだ 3 構成を実時間（M4 / M5）と議事録の質（M3）で比べた。どの案も速報は使わない。
測定機は RTX 3050 6GB / Vulkan / NVIDIA 616.92 / Whisper.net 1.9.0。実時間の計測は 2 音源に同じ音声を流す厳しい条件で行った。

### 案 A — small-q5_1 × 上限 6 秒 × 発話終了の無音 0.8 秒

- **内容:** ライブ用モデルを small-q5_1（whisper.cpp 配布の 5bit 量子化版）にし、遅れていないときの上限を 6 秒、
  ライブの発話終了の無音を 0.8 秒にする。速報は既定 OFF。
- **利点:** T199 の合格線（§5）をすべて満たした唯一の構成。GPU の負担は今とほぼ同じ（稼働の割合 46.2% / 47.7%）。
- **欠点:** 文字誤り率が今より上がる（15.8 分の会議で 30.47% → 36.14%、85 分の公開会議で 20.48% → 22.55%）。
  Zoom なしの発話 → 確定の p50 は 4.94 秒で、線（5 秒）に余裕が無い。
- **影響範囲:** `TranscriptionService`（区切りの上限・ライブの無音の設定化）、`AppSettings`、設定の既定値。スレッドの構成は変えない。

### 案 B — small のまま × 上限 6 秒 × 発話終了の無音 0.8 秒

- **内容:** モデルは今のまま、区切りだけ短くする。
- **利点:** 文字誤り率は案 A より少し低い（34.69%）。新しいモデルの入手が要らない。
- **欠点:** 推論の負担が今の約 1.2〜1.4 倍。Zoom なしで発話 → 確定の p50 が 5.60 秒、滞留の後半の傾きが今より大きく、
  議事録の誤りも今より 1 件多かった（合格線を 3 項目で満たさない）。

### 案 C — 何もしない（ADR-0007 の 2 段構成のまま）

- 速報は 1〜2 秒で出続けるが、議事録に残る確定の文は p50 8 秒台・p95 13〜16 秒遅れたまま。
- Zoom 中の滞留は 60 秒を超え続け（遅れの警告 REQ-REC-07 が出る量）、確定パスが追いつかない。
- 速報が CPU と常駐メモリを使い続ける。

### 案 D — base × 上限 6 秒 × 発話終了の無音 0.8 秒

- **内容:** さらに軽い base を使う。
- **利点:** 遅れと負担は最も小さい（発話 → 確定 p50 4.44 秒、推論の負担は今の 0.69〜0.96 倍）。
- **欠点:** 文字誤り率 50.77%（合格線 50% を超える）。85 分の会議では壊れた出力が 11 件、
  議事録では文を落とした所に別の文の年が期限として入るなど、作り話に近い誤りが出た（誤り 5 件。今は 3 件）。

## 決定

**案 A を採る。** ライブ文字起こしは確定パスだけの 1 段とし、既定を small-q5_1 × 遅れていないときの上限 6 秒 × ライブの発話終了の無音 0.8 秒にする。
速報パスは**既定 OFF** にし、コードは残す（消すかは、1 段の構成を実際の会議で使ってから利用者が決める）。

T199 の実測（案 A と今の構成。今の構成は速報なしで測った）:

| 指標 | 合格線 | 今の構成（small × 10 秒 × 2.0） | **案 A** |
|---|---|---|---|
| 発話 → 確定 p50 / p95（Zoom なし、M4） | ≤ 5 / ≤ 10 秒 | 8.26 / 13.41 秒 | **4.94 / 8.03 秒** |
| 発話 → 確定 p50 / p95（Zoom 中、M5） | 今の構成より小さい | 8.79 / 16.40 秒 | **5.33 / 11.67 秒** |
| 滞留の最大 / 60 秒超の時間（Zoom 中） | 今の構成以下 | 92.6 秒 / 34 秒 | **57.9 秒 / 0 秒** |
| 滞留の後半 15 分の傾き（Zoom 中） | 今の構成以下 | +1.155 秒/分 | +0.057 秒/分 |
| 文字誤り率（15.8 分の会議、M2） | 50% 以下 | 30.47% | 36.14% |
| 議事録の誤り / 欠落（85 分の公開会議、M3） | 誤りが増えない・欠落の差が揺らぎ以内 | 3 / 1 | 3 / 0 |
| クラッシュ / GPU ドライバーのリセット | 0 / 0 | 0 / 0 | 0 / 0（シェーダーキャッシュを空にした初回起動を含む） |
| Zoom の送信 fps（M5） | 今の構成に対する落ち 10% 以下 | — / 23 / 22 fps | 23 / 24 / 23 fps（落ち無し） |
| アプリの CPU p95 | 全コアの 25% 以下 | 3.9% | 6.2% |

決め手は **議事録に残る文の速さと、Zoom 中に確定パスが追いつくこと**。速報（p50 1.2 秒）ほど速くはないが、
議事録に使う確定の文は今より 3〜4 秒早く出て、Zoom 中も滞留が 60 秒に届かない。文字誤り率の悪化は、議事録の誤り・欠落を増やさなかった。

あわせて決めたこと（T199 の E5）:

- **確定パスの `audio_ctx` は 1500 のまま。** 段階にすると呼び出しの中央値は速くなるが、文字誤り率が 3 構成とも悪化した。
- **遅れているときの扱いは変えない**（上限 20 秒・早期確定の抑止。REQ-TRX-LIVE-10 / 13）。変えるのは遅れていないときの上限と、ライブの発話終了の無音だけ。
- **ファイル文字起こしの無音分割（`SilenceMergeGapSeconds` 2.0 秒。REQ-CFG-06）は変えない。** ライブの発話終了の無音は別の設定にする。
- **GPU での推論は `WhisperTranscription` の 1 本の列のまま**（ADR-0007「決定」7、20-architecture-standards.md §3 規則 6）。

## 結果

- **良くなること:**
  - 議事録に残る確定の文が、発話から p50 約 5 秒で出る（今は 8〜9 秒）。
  - Zoom 中も確定パスが追いつき、遅れの警告（REQ-REC-07）が出にくくなる。
  - 速報を止めるので、既定では CPU の速報スレッドと速報用モデルの常駐が無くなる。
- **悪くなること・受け入れるコスト:**
  - **話している最中の 1〜2 秒の字幕が既定では出なくなる**（速報を ON にすれば今までどおり出る）。
  - ライブの `.txt` の文字誤り率が上がる（+2〜6 ポイント）。質が要るときはファイル文字起こしで大きいモデルに起こし直す。
  - 区切りが短いので Whisper の呼び出しが約 1.8 倍に増え（30 分で 367 → 643 回）、文の途中で切れる箇所が増える。
  - small-q5_1 の入手と登録を利用者に案内する必要がある（推奨モデルの案内）。
  - Zoom なしの発話 → 確定の p50 は線ぎりぎり（4.94 秒）で、機械や会議の条件によっては 5 秒を超えうる。
- **後戻りのしやすさ:** 高い。モデル・区切りの上限・ライブの無音・速報の有無はすべて設定で戻せる
  （small × 10 秒 × 2.0 秒 × 速報 ON にすれば ADR-0007 の構成に戻る）。速報のコードは消さない。
