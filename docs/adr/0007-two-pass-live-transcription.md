# ADR-0007 — ライブ文字起こしを「速報パス」と「確定パス」の 2 段にする

> **状態:** 提案中 — 速報パスの実行場所（案 A / 案 B）は [T182](../tasks/T182-provisional-pass-measurement.md) の実測で決める。
> 決まった時点で本 ADR の「決定」を確定させて承認済みにする（承認前なので本 ADR 自体を直してよい）。
> **日付:** 2026-09-27
> **関連タスク:** [T181](../tasks/T181-two-pass-live-transcription-design.md)（本 ADR の起票）/
> [T182](../tasks/T182-provisional-pass-measurement.md)（実測と決定）/ T185〜T188（実装）
> **関連 ADR:** [ADR-0003](./0003-speaker-diarization-with-sherpa-onnx.md)（sherpa-onnx はファイル経路のみ）、
> [ADR-0006](./0006-mainviewmodel-split-reevaluation.md)（`MainViewModel` の再評価契機）

## 背景

利用者の依頼（2026-09-27）:

> 文字起こしのリアルタイム性を高めたい。Zoom の文字起こしのように、ストリーミング的にほぼリアルタイム・
> 精度無視で文字起こしをしていき、後からコンテキストに従って補正していくのが理想。
> GPU（Vulkan / CUDA）で Zoom 会議中でも現実的なパフォーマンスを維持できることが必須条件。

今の仕組みでは、これを満たせない。

- **表示が遅い。** 行が出るのは「発話の終わり＋ 2 秒の無音」か「20 秒たまった」後の推論が終わってからで、
  通常時でも 5〜18 秒遅れる（[T175](../tasks/T175-live-transcription-throughput.md) §2-1）。
  話し続けている間は何も出ない。
- **短い入力は割高。** whisper.cpp はエンコーダを 30 秒窓で回すため、5 秒の音声でも 1 回 1.91 秒かかる
  （RTX 3050 6GB / Vulkan / `ggml-small`。T175 §2-3）。今の確定用モデルを 1 秒ごとに回して途中経過を出すことはできない。
- **GPU は並列に使えない。** ggml の Vulkan バックエンドは、同じ GPU に対して 2 つのスレッドが
  それぞれのコンテキストで同時に推論すると落ちる（[ggml-org/ggml#1087](https://github.com/ggml-org/ggml/issues/1087)。
  直列化すれば落ちない）。Whisper.net の `WhisperProcessor` は自インスタンスの呼び出ししか直列化しない。
- **Zoom 会議中は GPU・CPU を取られる。** 空いているマシンでの能力は実時間の約 5.5 倍で、
  それ以上遅くされると遅れが発散する（T175 §2-4）。速報のために確定パスの GPU 時間を削れば、この余裕がさらに減る。

## 現状

- ライブ文字起こしは `TranscriptionService` の専用スレッド `WhisperTranscription` が 1 本だけで行う
  （[02_architecture.md §4](../spec/02_architecture.md#4-スレッドモデル)）。
  マイクとスピーカーを別々の音源として持ち、1 秒ごとに確定条件（REQ-TRX-LIVE-04）を満たしたチャンクを Whisper に掛ける。
- 結果は `SegmentTranscribed`（`Action<string>`）で 1 行ずつ通知され、`.txt` へ追記される（REQ-TRX-07）。
  行を後から書き換える仕組みは、画面にもファイルにも無い。
- `WhisperFactory` はライブ用に 1 つ。ファイル文字起こしで別のモデルを選んだときだけ、その実行の間 2 つ目を作る
  （REQ-TRX-04 / REQ-TRX-FILE-17。2 つ載せても 6GB に収まることを T163 で実測済み）。
- Whisper.net 1.9.0 は `ProcessAsync` のたびにネイティブの状態（`whisper_init_state`）を作り直して解放する
  （`WhisperProcessor.GetWhisperState`）。processor の生成自体は引数を詰めるだけで軽い。
- whisper.cpp の既定は `no_context = true` で、今のライブ経路は前の文脈を一切使っていない（`WithPrompt` も未使用）。

## 選択肢

共通の前提（どの案でも変えないもの）:

- **確定パスは今の仕組みのまま。** 区切り方（REQ-TRX-LIVE-04 / 10 / 12 / 13）・停止時の吐き切り（REQ-TRX-LIVE-11）・
  `.txt` の書式（REQ-TRX-07）を変えない。
- **速報のエンジンは Whisper の軽量モデル**（tiny / base）とする。登録済みモデル（REQ-CFG-08）から選ぶ。
  sherpa-onnx を使う案は案 D として検討し、利用者の判断（2026-09-27）で採らない。

### 案 A — 速報も GPU で、確定パスと同じスレッドで直列に回す

- **内容:** `WhisperTranscription` スレッドが、確定チャンクの合間に速報を差し込む。
  速報に使う時間の割合（duty）に上限を置き、確定の滞留が増えたら速報を間引く・止める。
- **利点:** スレッドが増えない。GPU が 1 本の列で使われるので、Vulkan の同時実行クラッシュは起きない。
  速報も GPU で速い。
- **欠点:**
  - **速報の遅れに下限がある。** 確定の呼び出しが 1 回終わるまで速報を出せない。
    20 秒チャンクで 3.63 秒（空いているとき）、Zoom で 2 倍遅くなれば 7 秒前後。字幕がいちばん欲しい「話し続けている間」ほど止まる。
  - 確定と速報で GPU の時間を取り合う。確定が遅れているときほど速報を止める必要があり、両立しない。
  - 確定のスレッド（REQ-TRX-LIVE-04 の 1 秒ポーリング、T129 で「変えない」とした箇所）に手を入れる。
- **影響範囲:** `TranscriptionService.TranscriptionLoop` / `ProcessChunk`。

### 案 B — 速報は CPU 専用の別スレッドで並列に回す（第一候補）

- **内容:** 速報用の 2 つ目の `WhisperFactory` を `UseGpu = false` で作り、新しい専用スレッド
  `ProvisionalTranscription` で回す。確定パスは今の `WhisperTranscription` スレッドのまま、GPU を独占する。
  - スレッド数は 4 以下、スレッドの優先度は `BelowNormal`。
- **利点:**
  - 確定パスに一切手を入れない。GPU の使い方は今と同じなので、「Zoom 中に確定が追いつくか」は今と変わらない。
  - 速報が確定の呼び出しを待たないので、遅れの下限が無い。
  - CPU コンテキストは Vulkan の同時実行クラッシュの対象外（ggml#1087 でも CPU・CUDA の並列は正常と報告されている）。
- **欠点:**
  - **CPU を Zoom と取り合う。** 映像のエンコードや背景ぼかしは CPU も使う。キャプチャのコールバックや MP3 書き込み
    （`WriterLoop`）とも CPU を分け合う。スレッドの優先度は whisper.cpp 内部のワーカースレッドには継承されない。
  - スレッドが 1 本増える（スレッドモデルの変更。本 ADR の対象）。
  - tiny / base を CPU で回したときの速度と日本語の質は未測定。
- **影響範囲:** `TranscriptionService`（新しいスレッド・イベント）、`MainViewModel.LiveTranscript`、
  `LiveTranscriptWindow`、`AppSettings`、`SettingsWindow`。

### 案 C — 何もしない

- 表示の遅れは 5〜18 秒のまま残る。話し続けている間は何も出ない。
- 利用者が取れる手は、ライブ用に軽いモデルを選ぶこと（遅れは減るが、ファイルに残る文の質も落ちる）だけ。
- 依頼の中心（ほぼリアルタイムの表示）を満たせない。

### 案 D — 速報に sherpa-onnx（ReazonSpeech / SenseVoice）を使う

- 日本語専用・非自己回帰で、CPU でも速く、速報の質は Whisper tiny / base より良い見込み。
  sherpa-onnx はすでに依存にあるため、NuGet は増えない。
- ただし ADR-0003 の「ライブ経路では使わない」を変えることになり、新しいモデル形式の配布と管理 UI も要る。規模が大きい。
- **利用者の判断で採らない（2026-09-27）。** T182 で Whisper の軽量モデルが合格線に届かなかった場合に限り、改めて提案する。

## 決定

**2 段構成にすることを決める。速報パスの実行場所は、案 B を第一候補とし、T182 の実測で案 A / 案 B を確定させる。**

実測は Zoom 会議中に行い、次をすべて満たす案を採る（両方満たすなら案 B。確定パスに手を入れずに済むため）。

| 指標 | 合格線 |
|---|---|
| 速報の遅れ（発話 → 画面） | p50 ≤ 1.2 秒、p95 ≤ 2.0 秒 |
| 確定パスの処理能力 | 速報なしの 90% 以上 |
| `PendingSeconds`（30 分） | 増え続けない（遅れの警告 REQ-REC-07 が出ない） |
| クラッシュ | 0 件 |
| Zoom の映像 | フレーム落ち 10% 以下、目に見えるカクつき無し |
| アプリの CPU 使用率 | 全コアの 25% 以下 |
| MP3 | 音飛び無し |

どちらの案でも共通して、次を決める。

1. **速報はファイルに書かない。** `.txt` に入るのは確定パスの行だけで、書式とタイミングは今と同じ。
   速報を一度も書かないので、ファイルを後から書き換える仕組みは要らない。
2. **速報と確定の対応は、音源ごとの絶対サンプル位置で取る。** チャンクの連番では取らない。
   チャンクは 20 秒上限・ギャップ分割・遅延時の溜まり方で切れ目が変わり、連番では速報の範囲と一致しないため。
   確定パスは各チャンクを処理し終えるたびに、その終端位置を通知する（0 行・キャンセル・例外で終わったときも通知する）。
   ViewModel はそこまでの速報を消す。前のセッションの通知を捨てるため、セッション ID も付ける。
3. **速報は、文字起こしウィンドウに足す字幕帯に出す。** 既存の行一覧の中で差し替えることはしない。
   差し替えると、表示上限で古い行を捨てる処理（REQ-LIVEVIEW-04）、まとめて追加する処理（REQ-LIVEVIEW-09）、
   スクロールを後回しにするクラッシュ対策（REQ-LIVEVIEW-06 / 07、T128）のいずれとも衝突するため。
   ファイル文字起こしの行もこの一覧を通るので、一覧側は触らない。
4. **停止は速報を先に止める。** キャンセルして `StopCancelTimeout` まで join し、その後で確定パスを従来どおり上限なしで吐き切る。
   ワーカーが終わっていなければ processor を破棄しない（T117 の規則を速報スレッドにも適用する）。
5. **速報用モデルの読み込みは、確定用モデルと同じ「録音していないとき」に順番に行う。**
   ネイティブのログ観測（GPU 判定。REQ-TRX-02）はプロセス全体で 1 つなので、読み込みを重ねない。
6. **確定パスに文脈を渡す**（利用者の選択: 直前の確定文と用語集）。
   確定の呼び出しのたびにプロンプトを組み立てて processor を作る（生成は軽い）。
   採否は T182 の A/B で決める。誤りが次の文へ伝わるリスクがあるため、長さの上限・リセット条件・除外条件を設ける。
7. **速報パスで GPU を使うのは案 A を採った場合だけ。** 案 B なら、速報パスは GPU に一切触れない。

## 結果

- **良くなること:**
  - 話している最中から 1〜2 秒遅れで文字が出る（合格線を満たした場合）。
  - 確定の文は今と同じ品質か、文脈を渡すぶん良くなる。
  - 案 B なら確定パスの GPU 負荷は今と同じで、Zoom 中の遅れの出方も今より悪くならない。
- **悪くなること・受け入れるコスト:**
  - モデルが 1 つ多く常駐する（tiny 約 75MB / base 約 142MB。案 B なら CPU メモリ）。
  - 案 B はスレッドが 1 本増え、Zoom と CPU を取り合う。案 A は確定パスのスレッドが複雑になる。
  - 速報の日本語は粗い（利用者の前提どおり、精度は問わない）。
  - `MainViewModel` が大きくなる。すでに ADR-0006 の再評価契機（2,500 行）を超えているため、
    ViewModel に手を入れる T187 / T188 は T170（分割の判断）を片付けてから着手する（利用者の判断、2026-09-27）。
- **後戻りのしやすさ:** 高い。速報パスは設定で無効にでき（既定は無効）、無効なら確定パスだけが今と同じに動く。
  速報に関わるコードは新しいファイル（`TranscriptionService.Provisional.cs` など）にまとめ、切り離せるようにする。
