# T199 — ライブ文字起こしを「軽量モデル × 短い区切り」の 1 段で回す案の実測と判断

> **状態:** 進行中 — 2026-11-05 着手
> **台帳:** [docs/tasks/backlog.md](./backlog.md)

## 1. 目的

速報パス（[ADR-0007](../adr/0007-two-pass-live-transcription.md)）をやめ、確定パスを軽量モデル（base / small-q5_1）× 短い区切りで回す
「1 段」の構成に切り替えるかを、実機で測って決める。採るなら、ADR-0007 を置き換える ADR を書いて承認を得る。

利用者の依頼 (2026-11-04):

> 速報を作るよりも、軽いモデルでの出力間隔を短くする方向のほうがいいかもしれない。
> base にすると、文字起こし自体の精度は当然下がるが、議事録化する上ではそこまで支障がないと思われる。small-q5_1 でも良さそう。

**手元の実測からの見込み**（起票時の見立て。未検証）:

- 1 回の処理の p50（T182 の M1。RTX 3050 / Vulkan / flash 有効 / `audio_ctx` 1500）は、base × 4 秒で 0.78 秒、small × 4 秒で 1.49 秒。
- 音声 1 秒あたりの GPU 時間は、今（small × 10 秒）が約 0.16〜0.26 秒、base × 4 秒が約 0.20 秒、small × 4 秒が約 0.37 秒。
  base × 4 秒なら GPU の負担は今とほぼ同じまま、話し続けたときの遅れが縮む。small × 4 秒は負担が 1.5〜2 倍になる。
- 今の構成（速報なし・2 音源に同じ音声）の確定の遅れ p50 / p95 は、Zoom なしで 8.2 / 17.5 秒、Zoom 中で 12.2 / 38.8 秒。
  Zoom 中は滞留が最大 143 秒に達した（T182 の M5 / M4 条件 1）。軽量モデルなら処理の余裕が増え、ここも改善する見込みがある。
- 文字誤り率は、small の確定パスが 31.7%（文脈プロンプトあり。T182 の M6）、base は速報の条件（8 秒の句・プロンプトなし・80 トークン上限）で 46.4%（T182 の M2）。
  base を確定パスの条件で回したときの値と、small-q5_1 の速度・質は未計測。

### 4.1 構成の絞り込み（M2 → M3 / M4）

M2 の 18 構成から、基準の構成のほかに最大 3 構成を選ぶ。

1. 文字誤り率が 50% を超えるもの（T182 の「読めない」線）と、壊れた出力が基準の構成の 2 倍を超えるものを外す。
2. 音声 1 秒あたりの推論時間（M2 の「推論時間の合計 ÷ 音声の長さ」）が基準の構成の 1.5 倍を超えるものを外す（Zoom 中に滞留が発散しやすいため）。
3. 残りから、モデルごとに上限の最も短いもの（同じなら発話終了の無音が短いもの）を 1 つずつ選ぶ。
4. 選んだ構成を利用者に見せて確定する。

### 4.2 議事録の作り方と採点（M3）

**作り方:** 次のプロンプトに、参加者の一覧（利用者が書く。全構成で同じもの）と文字起こしの全文を入れる。
LLM とそのモデルは全構成で同じにする（§12 の 2）。

```text
以下は会議の文字起こしです。音声認識の誤りを含みます。
文字起こしだけを根拠に、次の 4 項目の議事録を日本語で作ってください。
文字起こしから読み取れないことは書かず、「不明」としてください。

1. 概要（3〜5 行）
2. 決定事項（箇条書き）
3. ToDo（1 行に 1 件。「内容／担当／期限」の形）
4. 論点・保留事項（箇条書き）

参加者: （参加者の一覧）

<<<文字起こしここから>>>
（文字起こしの全文）
<<<文字起こしここまで>>>
```

**正解リスト:** 基準の文から作った議事録 2 回分を突き合わせ、決定事項・ToDo（内容／担当／期限）・論点を 1 項目ずつ並べる。
会議に出席した利用者が正誤を確かめる。

**採点:** 各構成の議事録を、正解リストに対して 1 項目ずつ次のどれかに分ける。一次の採点は手元の Claude が行い、利用者が確かめる。

| 区分 | 意味 |
|---|---|
| 一致 | 中身・担当・期限・数字・固有名詞が合っている |
| 部分 | 中身は合うが、担当・期限・数字・固有名詞のどれかが違う |
| 欠落 | 正解リストにあるのに出てこない |
| 事実と違う | 正解リストに無く、会議の内容とも合わない（逆の内容を含む） |

「部分」と「事実と違う」を合わせて**誤り**と呼ぶ。議事録で危ないのは欠落より誤りなので、合格線は誤りを主に見る（§5）。

## 5. 合格線（案。§12 の 1 で確認する）

| 指標 | 合格線 |
|---|---|
| 発話 → 確定（Zoom なし、M4） | p50 ≤ 5 秒、p95 ≤ 10 秒 |
| 発話 → 確定（Zoom 中、M5） | 基準の構成より小さい |
| 滞留（M4 / M5） | 最大値と 60 秒超の時間が基準の構成以下で、後半 15 分の傾きも基準の構成以下 |
| 議事録の誤り（M3） | 基準の構成より増えない |
| 議事録の欠落（M3） | 基準の構成との差が、基準の文から作った 2 回の差（LLM の揺らぎ）以内 |
| 文字誤り率（M2） | 50% 以下 |
| クラッシュ / GPU ドライバーのリセット | 0 件 / 0 件（small-q5_1 は初回起動の条件を含む） |
| Zoom の送信 fps（M5） | 基準の構成に対する落ち 10% 以下 |
| アプリの CPU 使用率（M4 / M5） | 全コアの 25% 以下 |

Zoom 中の滞留を絶対値（60 秒以下）で縛らないのは、今の構成でも 2 音源に同じ音声を流す条件では 143 秒に達し、
速報の有無と関係なく割れていたためである（T182 の M4 条件 1）。1 段の構成がこれを改善するかは、基準の構成との比で読む。
