# T212 — ファイル文字起こしの中止を待っている間に閉じると、アプリ全体が操作できなくなる

> **状態:** 完了 — 2026-11-23
> **台帳:** [docs/tasks/backlog.md](./backlog.md)

## 1. 目的

利用者の報告 (2026-11-16、2026.10.18 のベータ版):「文字起こし中止操作中に強制終了するとアプリ全体が操作不能になる」。
どこで止まっているかを突き止め、待っている間に何が起きているかを見せ、待たずに終える道を残す。

## 2. 調べたこと

報告にはどの中止・どの強制終了かが無いため、コードで「中止を要求してから実際に止まるまでの間に閉じる」経路を洗い出した。

- **ダイアログの ×**（REQ-TRX-FILE-13）: 確認の後、中止の完了を**待たずに**閉じる（コメントどおり）。処理中の印（`IsTranscribingFile`）は立ったままなので、
  メインウィンドウの操作はすべて無効。ステータスバーは開始時の「音声ファイルから文字起こし中...」のまま。
- **メインウィンドウの ×**（REQ-TRX-FILE-14）: 確認の後、`ShutdownAsync` が中止の完了を**上限なしで**待つ。もう一度 × を押しても
  `ShuttingDown` で閉じるのを止めるだけで、何も起きない。
- 中止が効くのは推論の境界だけ（話者識別は REQ-TRX-DIA-12、Whisper は区間の切れ目）。推論が戻らなければ待ちは終わらない。
  なお 2026-10-18 18:28〜18:52 に GPU ドライバーのリセットが 4 件記録されている（WER のダンプ名）。報告の場面との関係は未確認。

再現（`C:\personal\dev\audio-capture-work\t212-cancelcheck\`。本体を同一プロセスで動かす。12 分の音声・話者識別あり・small）:
話者識別中に中止 → ダイアログを閉じる → メインウィンドウを閉じる。

| | 修正前 | 修正後（待つ） | 修正後（もう一度 × →「待たずに終了」） |
|---|---|---|---|
| ダイアログを閉じた後のステータス | 「音声ファイルから文字起こし中...」 | 「ファイル文字起こし: 中止を要求しました（話者識別が終わるまでお待ちください）」 | 同左 |
| メインの × の後のステータス | 変わらない | 「終了しています... 中止を待っています（もう一度閉じると、待たずに終了できます）」 | 同左 |
| もう一度 × | **何も起きない** | 「待たずに終了しますか？」 | 同左 →「はい」 |
| × から閉じ終わるまで | **86.4 秒** | 85.8 秒 | **0.1 秒** |
| プロセスの終了 | — | 正常 | 正常（推論は動いたまま。例外なし、終了コード 0） |

1 時間の音声なら話者識別だけで約 7 分かかる（音声長の約 0.12 倍）。

## 3. 決定事項

| # | 決定 | 結論 |
|---|---|---|
| D1 | 待つことは変えるか | **変えない。** 「中止して終了」の既定は今までどおり中止の完了を待つ（作りかけの出力を消すため。REQ-TRX-FILE-07） |
| D2 | 待っている間の表示 | 中止を要求した時点でメインのステータスにも注記を出し、終了待ちの間は「もう一度閉じると、待たずに終了できます」を出す |
| D3 | 待たずに終える道 | **待っている間にもう一度 × を押したら確認し、はいなら閉じる。** 自動の時間切れにはしない（中止がもうすぐ効くかどうかは利用者のほうが分かる） |
| D4 | 待たずに閉じるときの後始末 | **処理中のファイル文字起こしが使っている `TranscriptionService` / `SpeakerDiarizationService` は破棄しない**（推論中のネイティブ資源の破棄はプロセスを落とす。T117 と同じ規則）。録音デバイスの監視は止める |
| D5 | 録音の停止処理中にもう一度 × | **今までどおり何もしない。** メインウィンドウに「打ち切り」ボタンがあるため |
