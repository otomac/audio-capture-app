# T143 — Whisper のトークン時刻がセグメント末尾へ押し込まれる（対策は入れない）

> **状態:** 完了 — 2026-08-23
> **台帳:** [docs/tasks/backlog.md](./backlog.md)
> **関連:** [T137](./T137-token-level-speaker-attribution.md)（発話時間帯の導入）／
> [T142](./T142-diarization-attribution-root-cause.md)（発見元）／[T146](./T146-short-segment-embedding.md)

## 1. 目的

Whisper のトークン時刻がセグメントの時間枠を使い切ると末尾時刻へ押し込まれ（長さ 0 のトークン）、
`BuildSpeechSpans` がそれを捨てるため発話時間帯が実際の発話より手前で終わる。
起票時の見立てでは、これが T137 で残った誤り `#12`「へぇー」の原因である。
**現象の実在と、起票時に挙げた対策 2 つが有効かを実測で確かめる。**

## 2. 結論

**ソースは変更しない。現象は実在するが、起票時に挙げた対策はどちらも成立しない。**

1. **「飽和を検出したら次セグメントの開始まで発話時間帯を伸ばす」は原理的に効かない。**
   Whisper のセグメントは**隙間なく連続して並ぶ**ため、伸ばす余地が無い。
   飽和している 20 セグメントのうち **17 件で余地は 0 秒**、残り 3 件も 0.05〜0.49 秒である（§7-1）。
2. 余地の有無を無視して**強制的に伸ばすと、正しく取れていた区別を 1 つ失う**（4/4 → 3/4）。
   直った行は 0 件である（§7-3）。
3. **`#12` の誤りの原因は、起票時の見立て（末尾トークンの飽和）ではない。**
   切り出し位置を変えて 12 通りにデコードし直したところ、**「へぇー」は 12 回中 2 回しか現れず**
   （うち 1 回は本体と同じ切り方）、残り 10 回では同じ時間帯を前後の発話が連続して埋める（§7-2）。
   末尾が飽和していた `#11` の直後に「へぇー」が入る形そのものが、この 1 回でしか再現しない。

## 7. 実測

対象は基準音声（`20260822_150806.mp3` / 2 分 42 秒 / 58 セグメント / 話者 2 名）。
Whisper モデルは `ggml-large-v3-turbo-q5_0.bin`、GPU（CUDA）。

### 7-1. 飽和の実態と「伸ばす余地」

| 項目 | 実測 |
|---|---|
| 特殊トークンを除くトークン | 811 個 |
| うち長さ 0 のトークン | **67 個 (8.3%)** |
| 末尾（特殊トークンを除く最後）が長さ 0 のセグメント | **20 / 58 件 (34%)** |
| そのうち **次のセグメントの発話開始までの余地が 0 秒** | **17 / 20 件** |
| 余地があった 3 件 | `#2` 0.48 秒 / `#3` 0.49 秒 / `#12` 0.05 秒 |

起票時の数字（長さ 0 のトークン 67 個、末尾飽和 20/58 件）は再現した。
**新たに分かったのは「余地が無い」ことである。** Whisper のセグメントは
`22.00-24.00` → `24.00-25.00` → `25.00-28.00` のように**隙間なく連続して並ぶ**ため、
「次のセグメントの開始まで伸ばす」という操作は 17/20 件で長さ 0 の変更にしかならない。

最も飽和がひどい `#11` がその典型である。

```
#11 22.00-24.00 before afterでいいエンジニアって変わんないんですよ
    トークン: before(22.00-22.42) … ニ(23.73-23.84) ア(23.84-24.00)
              って(24.00-24.00) 変(24.00-24.00) わ(24.00-24.00) ん(24.00-24.00)
              ない(24.00-24.00) んです(24.00-24.00) よ(24.00-24.00)   ← 末尾 7 トークンが飽和
    発話時間帯: (22.00-22.96) (23.00-23.70) (23.73-24.00)
#12 24.00-25.00 へぇー                                    ← 次のセグメントが 24.00 から始まる
```

### 7-2. 切り出し位置を変えた再デコード（どちらの時刻が正しいか）

同じ音声の一部だけを切り出して Whisper に掛け直し、絶対時刻へ戻して比べた。
切り出し位置を変えるとセグメントの区切り方も変わるため、**同じ発話がどこに置かれるかを
独立に何度も測れる**。「へぇー」の直前の発話（`#11` 相当）と直後の発話（`#13` 相当）の境目に注目する。

| 切り出し | `#11` 相当の終了 | 「へぇー」 | `#13` 相当の開始 |
|---|---|---|---|
| **本体と同じ 20 秒チャンク** | 24.00 | **24.00-25.00** | 25.00 |
| 0〜40 秒 | **24.26** | なし | **24.26** |
| 10〜40 秒 | **24.26** | なし | **24.26** |
| 15〜35 秒 | 25.00 | なし | 25.00 |
| 18〜38 秒 | 24.00 | **24.00-25.00** | 25.00 |
| 20〜35 秒 | 24.00 | なし | 24.00 |
| 21〜31 秒 | 24.00 | なし | 24.00 |
| 22〜28 秒 | **24.26** | なし | **24.26** |
| 23〜27 秒 | **24.26** | なし | **24.26** |
| 23.5〜26.5 秒 | (26.50 まで 1 セグメント) | なし | — |
| 24〜27 秒 | — | なし | 24.00 |
| 24.5〜27 秒 | — | なし | 24.50 |

読み取れること：

1. **「へぇー」は 12 回のデコードのうち 2 回しか現れない**（本体と同じ切り方、および 18〜38 秒）。
   残りでは、その時間帯を前後の発話が連続して埋める。
2. **細かい時刻が出た 4 回（0〜40 / 10〜40 / 22〜28 / 23〜27）は、いずれも境目を 24.26 秒に置く。**
   独立した切り出しで同じ値になるため、この 24.26 秒は偶然ではない。
3. Diarization が別話者を検出しているのは **25.12-25.44** である。
   本体の Whisper が「へぇー」を置いた **24.00-24.95** とも、再デコードの境目 **24.26** とも
   一致しない。
4. **したがって `#12` の誤りは「末尾トークンの飽和で発話時間帯が手前で切れた」ためではない。**
   飽和は同時に起きているが、原因ではない。より確からしいのは
   **重なって発せられた短い相槌を、Whisper が直列のセグメント列へ置く際に空いている枠へ入れた**
   という筋である（Whisper は同時発話を表現できない）。この読みは T142 の①「検出漏れ」・
   ②「同時発話」と同じ性質の問題であり、**トークン時刻の後処理では届かない**。

> **注意（この節の限界）:** 実音声を聴いていない。上の 4 点は「複数回のデコードが一致するか」
> という機械的な観察であり、24.26 秒が真の境目であることの直接の証拠ではない。
> ただし §7-3 のとおり、**どちらの時刻が正しくても採る対策は変わらない**。

### 7-3. 発話時間帯を伸ばす変種の採点

基準音声の話者区間（既定設定）を固定したまま、発話時間帯だけを変えて
本体の `TranscriptDiarizationMerger.Merge` に掛けた。評価軸は T138 と同じ 2 つ
（正解が分かっている 4 箇所の区別 ／ 既知の誤り 2 件の修復）。

| 変種 | 区別 | 既知の誤りの修復 | 使用 ID | 話者不明 | 既定から動いた行 |
|---|---|---|---|---|---|
| **既定（何もしない）** | **4/4** | 0/2 | 6 | 0 | — |
| 飽和した末尾を +0.2 秒 | **3/4** ✗ | 0/2 | 6 | 0 | 2 |
| 飽和した末尾を +0.3 秒 | **3/4** ✗ | 0/2 | 6 | 0 | 2 |
| 飽和した末尾を +0.5 秒 | **3/4** ✗ | 0/2 | 6 | 0 | 2 |
| 飽和した末尾を +1.0 秒 | **3/4** ✗ | 0/2 | 6 | 0 | 2 |
| 全区間を ±0.1 秒 | 4/4 | 0/2 | 6 | 0 | 1 |
| 全区間を ±0.2 秒 | 4/4 | 0/2 | 6 | 0 | 1 |
| 全区間を ±0.3 秒 | 4/4 | 0/2 | 6 | 0 | 1 |
| 全区間を ±0.5 秒 | 4/4 | 0/2 | 6 | 0 | 1 |

動いた行の中身：

- **末尾を伸ばす変種** — `#6` は同一人物の断片どうしの移動（無害）だが、
  `#23`「大事なのは上司としての人間だって」が **話者7 → 話者5** へ移る。
  話者5 は直後の `#24`「間違いなそう」に付いている ID であり、
  **`#24` の区別（正解が分かっている 4 箇所の 1 つ）が消える。**
- **許容幅の変種** — `#14`「イケてる人はエージェントもイケてる」が **話者0 → 話者5** へ移る。
  この行は直前の `#13` から続く同一話者の発話であり、**誤りが 1 件増える**。
  伸ばす量を 0.1 秒から 0.5 秒まで変えても、動く行はこの 1 行のまま変わらない。

**どの変種も、直した行は 0 件である。** 得るものが無く、失うものがある。

## 9. 未解決の質問（申し送り）

1. **実音声を聴いていない。** 起票時の指示は「実音声の聴取で確定させてから対策を選ぶ」だったが、
   本作業では聴取を行えなかったため、切り出し位置を変えた再デコード 12 通りで代替した（§7-2）。
   **聴取が必要なのは「24.00-24.95 と 25.12-25.44 のどちらに『へぇー』があるか」の 1 点だけ**であり、
   §7-3 のとおり**どちらであっても対策は「何もしない」で変わらない**。
   聴いて確かめたい場合は `20260822_150806.mp3` の 23〜27 秒を再生すること。
2. **Whisper が同時発話をどこへ置くかは制御できない。** §7-2 の 4 点目の読みが正しければ、
   相槌の時刻ずれは Whisper 側の性質であり、後処理では直せない。
   T142 ①（segmentation が相槌を検出しない）と合わせて、
   **相槌の話者を正しく取ることは現在の構成では成立しない。**
   これは T144（新しい segmentation モデルが出たら再評価）の対象に含まれる。
   本タスクからは新規タスクを起票しない — 打ち手が無い状態で票だけ増やさないため。

## 10. 計測方法（再現手順）

リポジトリには何も足していない。scratchpad の検証ハーネス（T138 のものを流用・拡張）で行った。

1. `whisper` — 本体と同じ手順（20 秒チャンク → 無音カット → `WithTokenTimestamps`）で
   セグメント・トークン・発話時間帯を JSON へ書き出す
2. `whispercrop`（本タスクで追加） — 音声の一部だけを切り出して Whisper に掛け、
   絶対時刻へ戻して JSON へ書き出す。無音カットは通さない（切り方の影響だけを見るため）
3. Python で発話時間帯を変種ごとに書き換え、本体の `TranscriptDiarizationMerger.Merge`
   （`InternalsVisibleTo` 経由で `internal` をそのまま呼ぶ）に掛けて TSV を作る
4. 4 箇所の区別と既知の誤り 2 件を機械的に採点する
