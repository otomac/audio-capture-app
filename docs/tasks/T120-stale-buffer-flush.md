# T120 — 供給が止まったバッファを時間経過で書き出す

> **状態:** 完了 — 2026-08-16
> **台帳:** [docs/tasks/backlog.md](./backlog.md)
> **PR:** T116 / T117 と同一 PR（T116 のギャップ分割の是正であるため分離しない）

## 1. 目的

ライブ文字起こしの `.txt` を読むと時刻が前後して見える問題を直す。
原因は書き出しの遅延であり、時刻の値そのものは正しい。

## 2. 調査結果

### 2.1 報告内容と実データ

「スピーカーをミュートで挟んで再開しても時刻がミュート時間を反映しない」との報告。
実際の出力ファイル（`20260816_221958.txt`、62 行）を機械的に検証した。

```
各ソース内の単調増加:
  マイク        7 行 / 逆行 0 件 / 範囲 22:21:18 - 22:22:35
  スピーカー   55 行 / 逆行 0 件 / 範囲 22:20:03 - 22:23:18

スピーカーの時刻ジャンプ:
  22:21:39 → 22:22:36 に 57 秒のジャンプ
```

**時刻の値は正しく、ミュート（実測約 57 秒）も正しく反映されていた。**
問題は**ファイルの行順**だった。

```
行順が時刻順になっていない箇所:
  行33: マイク    22:21:18  ← 直前は スピーカー 22:21:21
  行39: スピーカー 22:21:23  ← 直前は マイク    22:21:58   ★報告された箇所
  行56: マイク    22:22:18  ← 直前は スピーカー 22:22:55
```

### 2.2 根本原因 — 書き出し契機が「次のパケット待ち」

T116 時点でチャンクが確定する契機は 2 つしか無かった。

1. バッファが 20 秒分たまる
2. ギャップを検出する（＝**次のパケットが到着したとき**）

行 39 の経緯を追うとこうなる。

| 時刻 | 出来事 |
|---|---|
| 22:21:23〜39 | スピーカー音声が 16 秒分たまる（20 秒に届かない） |
| 22:21:39 | ミュート開始 → コールバック停止 |
| 22:21:39〜22:22:36 | バッファは 16 秒分のまま**放置**（契機 1 も 2 も成立しない） |
| 22:22:36 | ミュート解除 → 次のパケット到着 → 契機 2 が発火してようやく書き出し |

つまりその音声は **57 秒間バッファに座っていた**。その間にマイクは 22:22:05 まで
書き進んでいたため、後から追いついた行が古い時刻で現れた。

これは並び順以前に **書き出し遅延が無制限**という不具合である。ミュートしたまま
10 分放置すれば直前の音声は 10 分間書き出されない。

## 3. 修正

`ChunkTakeCount` を追加し、切り出し契機に「滞留時間」を加えた。

```
count >= 20秒分                          → 20 秒分だけ切り出す（T117 のまま）
age   >= 20秒 かつ count >= 0.2秒分      → バッファ全部を切り出す（追加）
上記以外                                  → 切り出さない
```

`age`（先頭サンプルが書き出されずに待っている実時間）は既存の純粋関数から求まる。

```csharp
age = _sessionClock.Elapsed - ChunkStartElapsed(BufferEndElapsed, count)
```

文字起こしループは 1 秒周期でポーリングしているため判定粒度は十分。

### 副作用が無いことの根拠

- **連続供給されているソースでは挙動が変わらない。** `age` ≒ バッファ長なので、
  20 秒到達と同時に成立し、既存の契機と一致する。
- **Whisper の呼び出し回数は増えない。** ギャップ分割は既に同じチャンクを作っており、
  それが早く出るだけ。T117 の実測どおり 1 回の推論コストは入力長にほぼ依存しない
  （0.2 秒入力 7745ms / 2.0 秒入力 7587ms）ため、細分化しない限りコストは増えない。
- **0.2 秒未満の断片は持ち越す。** 1 回の推論に見合わないため、セッション終了時に処理する。

### スコープ境界

**やらないこと**

- **終了時のファイルソート。** 依頼により不要と判断。本修正はズレの上限を
  約 20 秒に抑えるもので、**完全な時刻順は保証しない**（§6 参照）。
- **ウォーターマーク方式による書き込み遅延。** テキストが出るまで最大 20 秒以上
  遅れ、要件 6（リアルタイム表示サブウィンドウ）と相反する。
- **20 秒という値の設定化。** 現状はチャンク長と同じ定数として持つ。

## 6. テスト

- **`ChunkTakeCount_ReachedThreshold_TakesExactlyThreshold`** — 20 秒分到達で 20 秒分だけ
- **`ChunkTakeCount_FarOverThresholdAndStale_StillTakesOnlyThreshold`** — バックログが
  積んでも 1 回の呼び出しは 20 秒分に制限される（T117 の不変条件の維持）
- **`ChunkTakeCount_BelowThresholdAndFresh_TakesNothing`** — 通常の録音中は溜め続ける
- **`ChunkTakeCount_BelowThresholdButStale_TakesWholeBuffer`** — 報告事象の再現条件
  （16 秒分＋57 秒経過）で確定する
- **`ChunkTakeCount_ExactlyAtStaleAge_TakesWholeBuffer`** — 境界（経過＝しきい値）
- **`ChunkTakeCount_StaleButShorterThanTailMinimum_TakesNothing`** — 0.2 秒未満は持ち越す
- **`ChunkTakeCount_EmptyBuffer_TakesNothing`** — 空バッファ

> **テストで守れない範囲:** 実際の書き出しタイミングは実時間の経過を要するため
> ユニットテスト不可。下記の実測プローブで担保した。

### 実測（報告条件を実時間で再現 / 合成音を直接投入）

16 秒分供給 → 57 秒コールバック停止 → 再開、という報告どおりの手順を実行した。

| 項目 | 結果 |
|---|---|
| ミュート前 16 秒分の書き出し時刻 | **t=29.7s**（修正前は再開時の t=73s まで放置） |
| 出力された時刻 | `01:05:19 - 01:05:34` → `01:06:32 - 01:06:36` |
| 時刻ジャンプ | **58 秒**（57 秒のミュートを正しく反映） |
| ファイルの行順 | 時刻順 |
| `StopSession` 所要 | 3.1 秒 |

### 残る制約（正直な申告）

本修正は**ズレの上限を約 20 秒に抑える**もので、2 つのソースのチャンク完了順が
入れ替わる可能性自体は残る。実データの 3 箇所で言えば、

- 行 39 の違反（35 秒ズレ、原因は 57 秒の放置）→ **解消する**
- 行 56 の違反（37 秒ズレ）→ **解消する見込み**
- 行 33 の違反（3 秒ズレ）→ **残る可能性がある**

完全な時刻順が必要になった場合は、この上に終了時ソートかウォーターマーク方式の
マージを重ねる形になる（今回は依頼により対象外）。
