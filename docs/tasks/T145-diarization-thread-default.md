# T145 — 話者ダイアライゼーションの推論スレッド数の既定値を上げる

> **状態:** 完了 — 2026-08-23
> **台帳:** [docs/tasks/backlog.md](./backlog.md)
> **関連:** [T138](./T138-speaker-id-fragmentation.md)（発見元）／[ADR-0003](../adr/0003-speaker-diarization-with-sherpa-onnx.md)

## 1. 目的

`SpeakerDiarizationThreads` の既定が 1 で、話者ダイアライゼーションが不必要に遅い。
既定値を上げる。あわせて、起票時に確認事項として挙がっていた
「録音スレッドと競合しないか」を実測する。

## 2. 結論

**既定を `min(4, 論理コア数)` にする。**（本機では 4。論理コア数 20）

**起票時に記録されていた「1 スレッド 88.4 秒 → 4 スレッド 20.1 秒（4.4 倍）」は再現しない。**
同じ音声・同じモデル・同じ設定で測り直すと **1 スレッド 28.3 秒 → 4 スレッド 22.3 秒（1.27 倍）**である。
88.4 秒という値は**他の処理と CPU を奪い合っている最中に測られたもの**と分かった —
16 スレッド分の負荷を掛けながら測ると **1 スレッドで 85.0〜88.1 秒**が再現する（§7-3）。

したがって既定値を上げる根拠は「1.3 倍速くなる」ことではなく、
**負荷が掛かったときの落ち込みが小さいこと**である（負荷 16 で 1 スレッド 85 秒 対 4 スレッド 47 秒）。

## 3. スコープ境界

**やること**

- `AppSettings.SpeakerDiarizationThreads` の既定値を変える
- 要求仕様に既定値と根拠（結果は変わらない・上限 4 の理由）を書く
- README の誤った実測値（4.4 倍）を直す
- 既定値を固定しているテストを直す

**やらないこと（重要）**

- **既存の `settings.json` は書き換えない。** 設定ファイルに値が書かれている環境では、
  この変更は効かない（利用者が自分で直す）。理由は §4 D3。
- **`SpeakerDiarizationOptions` のクランプ範囲（1〜16）は変えない。**
- **Whisper 側のスレッド数には触れない。** 別系統である。
- **`AudioCaptureService` には触れない。** 競合は実測で確認するだけで、排他制御は入れない（§7-4）。

## 4. 決定事項

| # | 選択が必要だった点 | 結論 |
|---|---|---|
| D1 | 固定値にするか、論理コア数から決めるか | **`min(4, Environment.ProcessorCount)`。** 実測で 4 を超えても速くならず、8 を超えると遅くなる（§7-1）。一方、コアの少ない環境で 4 を強制する理由も無い |
| D2 | 上限を 4 にする理由 | **実測。** 2 分 42 秒の音声で 4 スレッド 22.3 秒に対し、8 スレッド 31.0 秒・20 スレッド 38.4 秒。15 分の音声でも 4 スレッド 107.6 秒に対し 20 スレッド 176.6 秒で、**20 スレッドは 1 スレッドより遅い** |
| D3 | 既存の `settings.json` を書き換えるか | **書き換えない。** 設定ファイルの値は利用者の意思表示として扱う。1 が「利用者の選択」なのか「古い既定値」なのかを区別する手段が無く、区別せずに上書きすると**設定を無視するアプリ**になる。代わりに README に書き、完了報告で申し送る（§9） |
| D4 | 録音スレッドとの競合に対処するか | **しない。** 10ms 周期のスレッドの遅れを測ったところ、推論スレッド 1 と 4 で差が無く（p50 5.54ms / p99 6.3〜6.5ms）、16 スレッド分の負荷を掛けても変わらなかった（§7-4） |
| D5 | 結果が変わらないことをどう保証するか | **実測で確認する（テストでは守れない）。** 1〜20 スレッドのすべてで話者区間 38 本が開始・終了・ID まで完全に一致した（§7-2） |

## 7. 実測

音声は 2 本。基準（`20260822_150806.mp3` / 2 分 42 秒）と会議 B（15 分 00 秒）。
埋め込みモデル・閾値は既定（campplus zh_en advanced / 0.5）。実行環境は 14 コア / 20 論理プロセッサ。

### 7-1. スレッド数と処理時間

| スレッド数 | 基準（2 分 42 秒） | 会議 B（15 分 00 秒） |
|---|---|---|
| 1 | 28.3 秒 | 140.4 秒 |
| 2 | 23.1 秒 | 117.2 秒 |
| **4** | **22.3 秒** | **107.6 秒** |
| 6 | 24.8 秒 | — |
| 8 | 31.0 秒 | 117.6 秒 |
| 10 | 28.6 秒 | — |
| 12 | 28.0 秒 | — |
| 16 | 30.0 秒 | — |
| 20（論理コア数） | 38.4 秒 | 176.6 秒 |

基準音声は 2 回追試した（1 スレッド 29.6 / 31.0 秒、2 スレッド 23.6 / 25.9 秒、
4 スレッド 22.3 / 25.5 秒、8 スレッド 24.9 / 24.6 秒）。**傾向は同じで、最良は 2〜4 スレッドである。**

**1 → 4 の効果は 1.27〜1.30 倍にとどまる。** 起票時の「4.4 倍」は再現しない（→ §7-3）。

内訳も測った。segmentation と embedding のスレッド数を別々に振ると（基準音声）:

| segmentation | embedding | 処理時間 |
|---|---|---|
| 1 | 1 | 26.0 秒 |
| 4 | 1 | 25.3 秒 |
| 1 | 4 | 21.5 秒 |
| 4 | 2 | 21.8 秒 |
| 2 | 4 | 19.6 秒 |
| 4 | 4 | 19.8 秒 |

**効いているのは embedding 側である**（segmentation だけ増やしても 26.0 → 25.3 秒）。
ただし本アプリは 1 つの設定値で両方に同じ数を渡しており、
それを分ける価値は無い（4:4 と 2:4 の差は測定誤差の範囲）。

### 7-2. 結果はスレッド数で変わらない

1 / 2 / 4 / 6 / 8 / 10 / 12 / 16 / 20 スレッドのすべてで、
**話者区間 38 本が開始時刻・終了時刻・話者 ID まで完全に一致した**（生成される ID も 16 種で同じ）。
会議 B でも全スレッド数で 167 区間 / 45 種が一致した。
**スレッド数は速度だけの設定である。**

### 7-3. 起票時の「4.4 倍」はどこから来たか

CPU を占有するスレッドを別に走らせながら測ると、次のようになった（基準音声）。

| 同時に走る負荷 | 1 スレッド | 2 スレッド | 4 スレッド | 1→4 の比 |
|---|---|---|---|---|
| なし | 26.3 秒 | 22.0 秒 | 20.2 秒 | 1.30 |
| 4 スレッド分 | 43.7 秒 | 39.7 秒 | 30.0 秒 | 1.46 |
| 8 スレッド分 | 58.5 秒 | 44.6 秒 | 37.0 秒 | 1.58 |
| 16 スレッド分 | **88.1 秒** | 60.4 秒 | 42.5 秒 | **2.07** |

**負荷 16 での 1 スレッド 88.1 秒は、T138 が記録した 88.4 秒とほぼ一致する。**
T138 の計測は複数の実験を並行させながら行われており、
**1 スレッドの測定だけが混雑した時間帯に当たった**と考えるのが自然である。
（4 スレッドの 20.1 秒は、負荷なしの 20.2 秒とよく一致する。）

**この表は既定値を上げる根拠でもある。** 空いているときの差は 1.3 倍だが、
**混んでいるときの差は 2 倍を超える。** 1 スレッドは他の処理に弱い。

### 7-4. 録音スレッドと競合しないか

10ms 周期で起きるスレッド（録音コールバック相当）を走らせ、
**予定より何 ms 遅れて起きたか**を Diarization 実行中ずっと測った。

| 推論スレッド | 同時に走る負荷 | 遅れ p50 | 遅れ p99 | 遅れ最大 |
|---|---|---|---|---|
| 1 | なし | 5.55 ms | 6.53 ms | 13.1 ms |
| 4 | なし | 5.54 ms | 6.44 ms | 12.1 ms |
| 1 | 16 スレッド分 | 5.54 ms | 6.52 ms | 6.8 ms |
| 4 | 16 スレッド分 | 5.54 ms | 6.26 ms | 6.7 ms |

**推論スレッドを 1 から 4 に増やしても、周期スレッドの遅れは変わらない。**
p50 の 5.5ms は Windows の `Thread.Sleep` の粒度そのもの（既定 15.6ms 刻み）であり、
負荷の有無でも動いていない。**排他制御を足す理由は無い。**

> **この測定の限界:** 実機の録音（WASAPI のキャプチャコールバック）そのものではなく、
> 同じ周期で起きるスレッドの代役で測っている。また 14 コア / 20 論理プロセッサの環境であり、
> **2 コアの環境では話が変わりうる**（そのため既定値は `min(4, 論理コア数)` にした）。

## 8. テスト一覧

- **`AppSettingsTests.DefaultValues_AreCorrect`**（既存・変更） —
  既定値が `min(4, Environment.ProcessorCount)` であることを固定する。
- **`AppSettingsTests.JsonDeserialization_MissingFields_UsesDefaults`**（既存・変更） —

> **テストで守れない範囲:** 「スレッド数を変えても結果が変わらない」ことは
> 実機のモデルと音声が要るためユニットテストにできない。§7-2 の実測で確認した。

## 9. 未解決の質問（申し送り）

1. **既にある `settings.json` には `"SpeakerDiarizationThreads": 1` が書かれている。**
   D3 のとおりアプリは書き換えないので、**利用者が手で直す必要がある**
   （その行を消せば新しい既定が使われる。`4` と書いても同じ）。
   話者ダイアライゼーションを使っている環境では、これをしないと本タスクの効果は出ない。
2. **2〜4 コアの環境では未測定である。** `min(4, 論理コア数)` は論理コア数が少ない環境で
   控えめになるよう選んだが、そこでの最適値は測っていない。

## 10. 計測方法（再現手順）

1. `diarize --threads N` — スレッド数を変えて話者区間と処理時間を JSON へ書き出す（§7-1 / §7-2）
2. `diarize --segThreads N --embThreads M` — segmentation と embedding を別々に振る（§7-1）
3. `contend --threads N --load M`（本タスクで追加） — CPU を占有するスレッドを M 本走らせながら
   Diarization を実行し、同時に 10ms 周期スレッドの遅れを測る（§7-3 / §7-4）
4. Python で JSON を突き合わせ、話者区間が完全一致するかを確かめる（§7-2）
