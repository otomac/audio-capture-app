# T182 — 速報パスの実測と方式の決定（ADR-0007 の確定）

> **状態:** 未着手
> **台帳:** [docs/tasks/backlog.md](./backlog.md)

## 1. 目的

[ADR-0007](../adr/0007-two-pass-live-transcription.md) の速報パスをどこで回すか（案 A: GPU で確定パスと直列／案 B: CPU の別スレッドで並列）を、
**Zoom 会議中の実機**で測って決める。決めた方式で ADR-0007 を承認済みにし、[T181 §11](./T181-two-pass-live-transcription-design.md#11-仕様変更の提案) の仕様変更を `docs/spec/` へ反映する。

## 2. スコープ境界

**やること**
- 使い捨ての計測ハーネスで M1〜M6（§4）を測る
- 速報用モデル（tiny / base）・`audio_ctx` の方針・間隔と duty の既定値・文脈プロンプトの採否を決める
- ADR-0007 の「決定」を確定させて承認済みにする。`docs/spec/`（01 / 02 / 04）へ反映する

**やらないこと（重要）**
- **計測ハーネスをリポジトリに入れない**（ローカルの作業用フォルダに置く。T142 と同じ扱い）
- **アプリ本体のコードを変えない**（実装は T185 以降）
- **確定パスの区切り方（REQ-TRX-LIVE-04 / 10 / 12 / 13）を変えない** — 計測で遅れが見つかっても、それは T183 か別タスクで扱う

## 3. 実施場所

**利用者の手元の Windows 機**（RTX 3050 6GB / Vulkan / 20 コア。T175 と同じ機械）で行う。
クラウド環境には dotnet も GPU も無いので、ここでは測れない。手元の Claude Code セッションに本書を渡して進めてよい。

- ハーネス: .NET 10 のコンソールアプリ。`Whisper.net` / `Whisper.net.Runtime` / `.Cuda` / `.Vulkan` を**アプリと同じ 1.9.0** で参照する
- 音声: T175 で使った実録音 2 本（62.7 分・15.8 分の会議）。16kHz モノラルへの変換はアプリと同じ手順（`TranscriptionService.DownmixResampleAppend` 相当）で行う
- 比較の基準にする文: 同じ音声を `ggml-large-v3-turbo` でファイル文字起こしした結果
- 負荷の記録: `nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv -l 1`、タスクマネージャー（または `typeperf`）の CPU、Zoom の「統計情報」（フレームレート）

## 4. 計測項目

| # | 測るもの | 条件 | 記録する値 |
|---|---|---|---|
| **M1** | 1 回あたりの費用 | エンジン {small-GPU, base-GPU, tiny-GPU, base-CPU, tiny-CPU} × 窓 {2, 4, 6, 8 秒} × `audio_ctx` {窓に合わせた段階, 1500} × flash attention {無効, 有効}（GPU のみ）。各 30 回 | 所要時間の p50 / p95。ネイティブログの `whisper_init_state` にかかる時間（呼び出しごとの固定費） |
| **M2** | 速報の質 | 15.8 分の会議を、D9 の句単位で速報として流す（tiny / base、`audio_ctx` 2 通り） | 基準の文に対する文字誤り率。壊れた出力（空・繰り返し・定型の幻聴）の件数 |
| **M3** | 並列で落ちないか | 確定（GPU・small）と速報（CPU・tiny または base）を別スレッドで同時に 30 分 × 2 回 | クラッシュの有無。確定パスの処理能力（速報なしとの比） |
| **M4** | Zoom 会議中 | M5 のリプレイを、Zoom 会議（カメラ ON）→ 同（仮想背景あり）の 2 条件で | 下の合格線の全項目 |
| **M5** | 実時間のリプレイ | 62.7 分の会議を 2 音源として実時間で流し、案 A と案 B の両方のスケジューラーで処理する | 速報の遅れ（発話 → 通知）の p50 / p95 / p99。確定の遅れ（発話の終わり → 確定行）。`PendingSeconds` 相当の推移 |
| **M6** | 文脈プロンプトの A/B | 15.8 分の会議の確定パスを、プロンプトなし／直前の確定文のみ／用語集のみ／両方の 4 通りで | 基準に対する文字誤り率。繰り返しや幻聴の件数。用語集の語が正しく出た回数 |

**M5 の読み方の注意:** T183（遅れているときの早期確定抑止が効かない不具合）が直っていない状態では、遅れたときの確定パスの挙動が本来の設計と違う。遅れが 60 秒を超えた区間は、そう注記して読む。

## 5. 合格線（ADR-0007「決定」の表と同じ。Zoom 会議中に測る）

| 指標 | 合格線 |
|---|---|
| 速報の遅れ（発話 → 画面） | p50 ≤ 1.2 秒、p95 ≤ 2.0 秒 |
| 確定パスの処理能力 | 速報なしの 90% 以上 |
| `PendingSeconds`（30 分） | 増え続けない（遅れの警告 REQ-REC-07 が出ない） |
| クラッシュ | 0 件 |
| Zoom の映像 | フレーム落ち 10% 以下、目に見えるカクつき無し |
| アプリの CPU 使用率 | 全コアの 25% 以下 |
| MP3 | 音飛び無し（ハーネスでは測れないので、T186 以降の実アプリで確かめる） |

**速報の質（M2）は合否に使わない**（利用者の前提は「精度は問わない」）。ただし、文字誤り率が 50% を超えて読めないなら tiny ではなく base を選ぶ。base でも読めなければ、ADR-0007 の案 D を利用者に再提案する。

## 6. 決めること（本タスクの成果）

| # | 決めること | 決め方 |
|---|---|---|
| E1 | 案 A / 案 B | §5 をすべて満たす案。両方満たすなら案 B。どちらも満たさないなら、満たさなかった項目と数字を添えて利用者に相談する |
| E2 | 速報用モデルの推奨 | tiny / base のうち、E1 の方式で合格し、文字誤り率の低いもの |
| E3 | `audio_ctx` の方針 | 窓に合わせた段階で質が保てるならそれを使う。保てないなら 1500 固定 |
| E4 | 間隔と duty の既定値 | M5 で合格線を満たした設定 |
| E5 | 文脈プロンプトの採否と既定値 | M6 で文字誤り率が下がり、繰り返し・幻聴が増えない組み合わせを既定 ON にする。増えるなら既定 OFF |
| E6 | flash attention | 確定パスが有意に速くなるなら、別タスクとして起票する（本機能には含めない） |
| E7 | 速報の既定 ON / OFF | 合格したら ON に変えるかを利用者に確認する（T181 §9 の 1） |

## 9. 未解決の質問

1. **Zoom 会議の相手** — 選択肢: 自分 1 人の会議（カメラ ON）／実際の会議。*既定案: 自分 1 人の会議で測り、実際の会議では T186 以降の実アプリで計測ログを取って確かめる。*
2. **CUDA の確認** — T175 の機械は NVIDIA の GPU（RTX 3050）だが、Vulkan ランタイムで動いていた。CUDA ランタイムでも測るか。*既定案: CUDA が使えるなら M1 と M4 だけ CUDA でも測る（Vulkan と違い、CUDA は同じ GPU の並列実行で落ちないとされるため、案 A の結果が変わりうる）。*

## 10. 前提

- T175 と同じ機械・同じ会議音声が使えること。
- 計測ハーネスのスケジューラーは T181 の D9〜D12 どおりに作る。実アプリの実装（T185 / T186）は、ここで合格した設定をそのまま使う。
